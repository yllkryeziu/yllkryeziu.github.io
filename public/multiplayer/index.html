I built a multiplayer world in Rust that moves regions between three worker processes while players keep sending commands. When a crowd gathers in one corner, ownership changes to spread the load.

The challenge is transferring the right to change state without losing acknowledged work. The experiments below compare placement policies, walk through a handoff, and test what survives when a worker crashes.

A balanced map is not a balanced workload

Splitting a world into three equal stripes looks reasonable. It even works—until everyone runs toward the same event. Two workers have room to spare. The third has a queue that grows faster than it can drain.

A stateless load balancer would send the next request somewhere else. Here, the next worker needs the state: which commands have already happened, the last sequence number, and the latest presence of every player in the region.

The question is not just where should this work run? It is how do we change the answer while the work is still happening?

I built a small world to make that distinction visible. The clients submit a deterministic stream of movement samples. Three separate Rust processes execute real CPU work and own regional state. A coordinator routes commands and proposes changes to the ownership map.

Moving a writer

A naive copy-and-switch has a race: copy the state, accept another command at the old owner, then publish the new one. That command was acknowledged. Its effect is now missing.

The handoff needs a boundary that both workers agree on. I use an ownership epoch, a monotonic sequence per region, and a snapshot followed by an ordered tail of state changes.

During the final seal, the coordinator buffers new arrivals for that region. A priority seal freezes the old writer at its last executed sequence. The destination applies the computed tail and advances the epoch before the directory changes. Every unacknowledged command is then forwarded in order; deduplication covers effects whose receipts were still in flight.

Operation IDs travel with the snapshot. A retry returns the existing receipt. An old epoch fails before mutation. The guarantee is exactly-once effects for retained operation IDs within a coordinator session. Durable workers also retain their receipts across a local process restart; the network can still deliver requests more than once.

The first version moved too late.

A global FIFO service queue exposes a second bottleneck. A migration barrier waited behind work for unrelated regions, so a busy worker could spend seconds waiting to hand off its state. The placement decision was already aging before it took effect.

The worker now uses fair per-region mailboxes, with a four-command execution quantum. Prepare and seal controls cut at the executed prefix; queued commands continue at the new owner. Other regions keep making progress. The tail carries computed state deltas, so the destination does not repeat the expensive CPU kernel. The FIFO path remains available as a baseline. The ablation below measures the scheduling package, including priority cutover, against that baseline.

Choosing where to move

Players interact with their surroundings. A region periodically reads neighboring occupancy and receives those observations at its owning worker. Place neighboring regions on different workers and those observations cross process boundaries.

A CPU-only greedy scheduler can reduce the hottest worker’s demand while fragmenting a closely interacting crowd. To account for that cost, the adaptive scheduler treats regions as vertices and proximity demand as weighted edges.

A bounded local search over single regions and adjacent pairs.
Lower is better. Moving nothing is a valid decision.

Pairs matter: two neighbors can be worth moving together even when either move alone cuts an expensive edge. The search is deliberately small—36 candidate regions and their adjacent pairs—so the controller’s cost remains inspectable.

CPU demand and edge weights are estimates. The movement penalty is a normalized proxy, not an exact byte-cost model. The benchmarks therefore report both the weighted graph cut and the actual routed proximity payload.

Knowing when to stay put

A crowd that keeps reversing direction is a trap for a reactive scheduler. Migration itself consumes time and resources. Optimizing every noisy sample can turn the controller into another source of load.

01

Smooth the signal

An EWMA with α = 0.3 dampens instantaneous regional demand.

02

Demand a real gain

A proposal must pay its movement penalty and improve the objective by 0.035.

03

Give it time

A region waits 3.5 seconds before another move. At most 8 regions move in a 4-second window.

04

Check it again

Before acting, validate the proposed source and re-score the move against the latest observations.

The planner runs on a separate blocking thread. It returns a proposal, not authority. The coordinator checks that proposal before starting a handoff. This separation lets commands continue while placement is computed—and makes stale decisions an explicit concern.

Read the measurement contract +

One host, three independent Rust worker processes. Each presence command evaluates a synthetic potential field with 32,000 iterations and stores the result. No sleep-based service budget. These fixed benchmark runs use a 900 ops/s target; per-worker calibration is recorded separately. Interactive sessions size their arrival rate from a short CPU calibration, so the rally flag remains useful on different machines.

Latency runs from coordinator submission to receipt of the worker’s batch acknowledgment. It includes queueing, TCP, execution, buffering, and handoff. Workload generation is open-loop; producer scheduling delay is recorded. Startup and transition samples remain in the results. Missing migration samples are null, never zero.

Proximity bytes count four routed application payloads per remote exchange; TCP framing and unrelated client traffic are excluded. Only one proximity round can be outstanding; skipped rounds are recorded, so a smaller byte count alone does not prove better locality. Weighted cut is a workload estimate independent of completed reads. Overload area integrates demand above the planner target and is not hardware CPU utilization or the DRV metric from the cited paper.

The replay audit verifies sequence count, effects, ordered digest, dedup history, presence values, and exactly one current writer. Cross-region observations are eventually consistent and excluded from a global transaction oracle.

Inspect the committed raw per-command latencies, handoff events, environment, workload hashes, and configuration. Short experiments on one machine support this demo’s comparisons, not internet-scale capacity claims.

Transactions and recovery

A regional bank holds 100 coins. Alice and Bob each read that balance and try to withdraw 60. With blind writes, both set the bank to 40 and credit their own account. The world now contains 160 coins. Each write succeeded; the combined result is wrong.

The worker’s versioned store gives both players the same snapshot. Under snapshot isolation, the first write set commits atomically. The second finds that the bank changed after its read version and receives WRITE_CONFLICT. Older readers still see 100.

Snapshot isolation has a limit. Two guards each see the other on duty and update different keys to go off duty. Both commit, leaving zero guards. This write skew passes write/write conflict detection. Serializable execution would need stronger validation or locking; this engine deliberately does not claim it.

What makes an acknowledgment survive?

Each worker appends a complete transaction write set to a framed, checksummed redo log. It holds the reply until sync_all succeeds. Group commit lets several writes share that sync. Reads and migration controls are barriers: no response exposes an unsynced change, and a source’s frozen state reaches disk before the destination receives authority.

  1. Migrate the region. Transfer its versions, committed transaction IDs, and ownership epoch.
  2. Checkpoint, then commit once more. Sync the snapshot, atomically publish it, and leave a real log tail.
  3. Kill the destination process. Restart it from its own files. Compare state, retry the winning withdrawal, and confirm the old owner still rejects writes.

The restart uses a checkpoint plus log replay. An incomplete final record is discarded as a unit; a complete record with a bad checksum stops recovery. Checkpoints shorten replay without deleting the log in this bounded teaching engine.

Where redistribution stops helping

Put almost every player in one region. Move that region anywhere you like: its CPU demand is still larger than one worker’s capacity. The remaining machines cannot help until the unit of ownership gets smaller.

Compare “One indivisible region” in the measurements above.

Redistribution changes the address of the bottleneck. Splitting or refining the region would change its size.

There are other limits. Rapidly changing traffic can make migration lose to static ownership. A locality preference can preserve an overloaded cluster of regions. Moving to an idle worker still consumes destination CPU and transfer bandwidth.

A crash during handoff still stops writes for the affected region. The protocol does not invent a new owner. The tests kill a source during a handoff and verify that the destination never becomes a second writer. The storage experiment recovers a worker after a completed handoff, with the coordinator and local disk intact.

Durable replicated state, a consensus-backed directory, multi-host deployment, adaptive region splitting, and atomic cross-region interactions would be separate extensions with separate guarantees.

What this demonstrates

A distributed system has to live between its old decision and its new one. That interval is where ownership, ordering, queues, and good intentions meet. This world is small enough to inspect that interval—and real enough to measure it.
